Überblick und Identität

Hubklasse 09 kann auf Geräte- oder Interface-Ebene stehen. Ein Hub-Eintrag bezeichnet Topologie; er bestimmt weder ein Gehäuse noch eine Dockingstation oder die Elektronik hinter jedem Port eindeutig.

Dies ist ausdrücklich ein Klassen-, Transport- oder Treiberkontextprofil. Es identifiziert kein exaktes numerisches Produkt.

Ein numerischer Match belegt eine Kandidatenfamilie im geprüften Quellenrahmen. Verkaufsnamen, Platinenvarianten, Subsystembedingungen und erfolgreiche Funktion bleiben getrennte Fragen.

Treiber und Bindung

Die Hub-Bindung ist in usbcore statt in einem eigenständigen hub-Modul implementiert und passt auf beide Formen des Klassendeskriptors. Portpfade in lsusb -t helfen dabei, Abbrüche einem vorgeschalteten Ast zuzuordnen; nachgelagerte Interfaces bleiben eigenständig gebunden.

  • usbcore — Kernel-Treiber-/Modulkandidat

Lesende Diagnose

Führe jeden angezeigten Befehl einzeln aus. Ersetze Großbuchstaben-Platzhalter durch betroffenes Gerät, Schnittstelle oder Modul aus deiner Ausgabe. Hier wird nichts ausgeführt. Auch lesende Ausgaben können private Kennungen enthalten.

Interfaces und ausgehandelte Geschwindigkeit prüfen

lsusb -t

Diese lesende usbutils-Abfrage benötigt normalerweise kein sudo. Driver gehört zum angezeigten Interface, die Geschwindigkeit zur ausgehandelten Verbindung. Weitere Interfaces desselben Geräts können andere Treiber verwenden.

Treiberlink eines USB-Interfaces lesen

readlink /sys/bus/usb/devices/INTERFACE/driver

INTERFACE durch ein vorhandenes Interface wie 1-2:1.0 ersetzen, nicht nur durch den Gerätenamen 1-2. Der Symlink wird ohne sudo gelesen; fehlt er, bleibt die Bindung unbestätigt.

Grenzen und passende Fehlerhilfen

Eine Hub-Liste belegt weder das verfügbare Leistungsbudget noch den ausgehandelten Lademodus oder die Signalqualität. Mehrere Einträge können logische Teile einer physischen Dockingstation sein.

Diese Anleitungen passen zu relevanten Befunden und behaupten keinen Fehler bei jedem Gerät dieser Familie.
