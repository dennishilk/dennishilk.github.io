BoringOS

An independent desktop operating system built from scratch — not Linux, not BSD and not a wrapper around another kernel. BoringOS now boots on the real Cthulhu machine into its own persistent BoringWM desktop, accepts real USB keyboard input, launches native applications, tiles and closes them, survives closing the final window, and runs boringfetch inside the physical graphical terminal.boring is not a bug. it's the entire operating system now.

01 · Physical proof

The desktop is real now.

Cthulhu is no longer only a readiness target. BoringOS boots from the M61 USB image, hands off from the boot dashboard to BoringWM and remains usable as a native desktop.

HW

Cthulhu

AMD Ryzen 7 5800X3D, Gigabyte B550 VISION D, 32 GiB installed memory detected through SMBIOS and 57 PCI devices reported by boringfetch.

USB

Real keyboard path

A directly attached Holtek USB keyboard works through BoringOS xHCI Interrupt-IN → HID decode → input queue → boring-display → BoringWM.

WM

Persistent lifecycle

Open, tile and close native apps; close every window; the empty BoringWM desktop stays alive and applications launch again afterwards.

02 · Native desktop

Kernel, services, WM and applications are all BoringOS.

PID 1 starts the Ring3 display stack from BoringFS. There is no X11 or Wayland underneath it.

03 · USB

xHCI works physically — topology is the next problem.

The bounded USB stack is now proven on real hardware for the active controller, direct HID keyboard input and USB Mass Storage. The remaining gaps are architectural rather than “does USB work at all?”.

04 · Graphics

Software-rendered today. Native GPU driver later.

BoringOS currently composes the desktop on the CPU and presents into the firmware/Limine framebuffer. The GPU scans that framebuffer out to the monitor, but BoringOS does not yet program AMD graphics hardware itself.

NOW800×600 framebufferThe current physical GOP/firmware mode is 800×600×32 with pitch 3328.
NOWCPU compositionboring-display/BoringWM render in software; the present path copies pixels into the scanout framebuffer.
NEXTBetter GOP modeGet a native or otherwise useful monitor resolution before building a full vendor GPU driver.
LATERAMD driverNative modesetting, VRAM/GTT and GPU command submission are intentionally much later work.
05 · Storage + BoringFS

The physical system boots from its own USB-root path.

BoringFS is BoringOS's own filesystem. M61 combines Limine boot files and a writable BoringFS root on one fixed-layout 96 MiB USB image.

FS

BoringFS

Own codec, validator, formatter, boringfsck, kernel mount support and writable operation.

USB

Physical root

xHCI USB Mass Storage, Bulk/BOT/SCSI and the fixed BoringFS slice are physically reached on Cthulhu.

SATA

Other path

Bounded synchronous AHCI/SATA read, write and flush support remains verified alongside VirtIO reference storage.

07 · Current limits

The remaining rough edges are visible — and useful.

The physical machine is now exposing exactly which bootstrap assumptions should be removed next.

Processes

KERNEL_PROCESS_MAX and KERNEL_TASK_MAX are both 8. That is why only about two full terminals fit while roughly five single-process apps can tile.

USB topology

No hub enumeration and no multi-xHCI ownership yet. Direct keyboard works; the hub-connected mouse is not yet supported.

Graphics

Firmware framebuffer + CPU composition. No native AMD/NVIDIA/Intel GPU driver yet.

System breadth

No networking, audio, NVMe or SMP runtime yet. BoringOS still prefers a truthful small system over pretend support.

Source of truth

The repository contains the implementation, tests and exact physical M61 branch. BoringOS is MIT licensed and primarily written in C.
