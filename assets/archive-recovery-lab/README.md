# Archive Password Recovery Lab — ZIP / RAR4 / RAR5 / 7Z / PDF

Routes: `/museum/archive-recovery-lab/` and `/de/museum/archive-recovery-lab/`.

This release includes tested **browser-local recovery and downloads** for narrowly validated ZIP, RAR4, RAR5, encrypted 7Z and PDF security revisions. Every claimed supported variant has independent fixtures. Unsupported files and unverified variants must still be rejected. No blog article is included; Worldnode deployment remains manual.

## Support matrix

| Container / encryption | Recognition | Password verification | Independent extraction | Local output |
|---|---|---|---|---|
| ZIP / traditional ZipCrypto | Yes | Real key update + header rejection, then decompression + CRC-32 | Fresh parse; every entry checked | Individual files + new unencrypted ZIP |
| ZIP / WinZip AES-128, AES-192, AES-256, AE-1 and AE-2 | Yes | PBKDF2-HMAC-SHA-1 (1,000 rounds), password-verification bytes, then authenticated extraction | Fresh parse; HMAC authentication and applicable integrity checks | Individual files + new unencrypted ZIP |
| RAR4 / encrypted archive headers (RAR3 crypto) | Signature, real WASM archive inspection | 7-Zip 24.09 WASM CPU, real candidates | Fresh WASM instance, full test and extraction | Individual files + ordinary ZIP |
| RAR5 / encrypted archive headers | Signature, real WASM archive inspection | 7-Zip 24.09 WASM CPU, real candidates | Fresh WASM instance, full test and extraction | Individual files + ordinary ZIP |
| 7Z / AES-256 + encrypted headers / LZMA2 | Signature, real WASM archive inspection | Native 7Z-specific AES/KDF via 7-Zip 24.09 WASM | Fresh WASM instance, full archive test and extraction | Individual files + ordinary ZIP |
| PDF Standard Security / R2 (RC4-40), R3 (RC4-128), R4 (AES-128), R6 (AES-256) | /Encrypt /R dictionary + qpdf validation | Genuine user-opening-password verification via qpdf WASM | Fresh qpdf pass, unencrypted export, qpdf check and independent pypdf parse | Decrypted PDF |

Supported ZIP compression: Stored (0), Deflate (8). Supported: data descriptors,
multiple files/directories, small ZIP64 archives. A single common password must
unlock **all** encrypted entries. Every success requires full independent
extraction before any password or output is released. A malformed, conflicting,
unsupported or excessive archive is rejected. A ZipCrypto header alone is never
success; the regression suite deliberately finds and rejects a header collision.

No GPU/Hybrid verification path is implemented or advertised. CPU Workers are
the only search engine. Optional WebGPU diagnostics distinguish a missing API,
a missing adapter, initialization failure and an available adapter with an
unsupported ZIP algorithm; they never invent GPU attempts or rates. There has
been **no physical RX 9060 XT validation** of this new lab.

## Privacy and architecture

- File/Blob byte ranges: signatures, bounded central directory, local headers.
  No arbitrary remote-URL input; no upload or third-party service.
- `zip-api.js` configures the vendored native-stream ZIP core with internal
  workers disabled. Recovery Workers are self-contained Blob scripts built from
  the same core, verifier and worker source. They load no further assets.
- Page CSP: `connect-src 'self'` only for same-origin WASM asset loading; `script-src 'self' 'wasm-unsafe-eval'`; `worker-src 'self' blob:`; no forms, external CDNs, base URLs, objects or remote fonts. Browser request auditing forbids uploads and remote requests.
- The general upstream ZIP package contains unused HTTP reader APIs. This app
  uses only BlobReader/TextReader; network tests and CSP enforce the boundary.
- Candidates are generated by the companion lab's **unmodified** `search.js`,
  dictionaries, transformations and packed indexes. The 488,971 base entries and
  source licenses are reused in place, never duplicated. Years start at 1984 and
  end at max(2035, current UTC year), capped at 9999.
- CPU workers receive bounded, disjoint batches of at most 64 candidates.
  Their reported deltas are checked against the assigned batch. BigInt counts
  and per-phase counts are exact; only completed reported checks are counted.
  On a match, other workers drain/cancel and all files are re-opened in a new,
  independent verification Worker.
- Current/average rates use completed real archive checks and active wall time,
  excluding preparation and pause. Estimates are shown after at least one
  second of observed work. Search time and independent-verification time are
  reported separately. No SHA-256 benchmark is reused.
- Pause stops at a candidate boundary. Hidden tabs pause; returning never
  silently resumes. Stop preserves reported checks; Reset terminates workers,
  removes passwords/results/files and revokes object URLs. No browser storage,
  service worker, private-data logging or automatic download is used.
- JavaScript/Blob garbage collection cannot guarantee secure memory erasure.
  Clipboard copy deliberately places the password on the user's clipboard.
- Demo creation passes only the resulting encrypted Blob into normal recovery;
  the known demo password input is cleared, and no password hint is transmitted
  to the search engine. The demo contains a real encrypted text and encrypted
  empty Deflate entry, validated by the same normal verifier.

## Limits and unsupported cases

ZIP input <=32 MiB; RAR4/RAR5/7Z/PDF input <=8 MiB; <=256 entries; central directory <=1 MiB; output <=16 MiB per
file and <=32 MiB total; declared expansion <=200:1; 1–4 CPU workers. Actual
stream output is bounded even if declared sizes lie. Filenames are displayed as
text. No entry is executed, rendered as document HTML, or recursively expanded.
Unsafe paths, Windows reserved names, symlinks, case/NFC collisions and
file/directory conflicts are rejected. The new ZIP preserves paths; individual
browser downloads use the final filename and never overwrite the source file.

Not supported: split archives, executable/SFX containers, Deflate64/BZip2/LZMA
ZIP entries, PKWARE strong encryption, encrypted ZIP directory listings,
archives with different passwords per entry, archives containing only empty
ZipCrypto payloads, or empty/malformed AES payloads without authentication.

Candidates currently cover the inherited **ASCII** dictionaries and printable
ASCII brute force. Known-character mode reduces only brute force using explicit
user-entered lengths/character sets; dictionary phases remain unchanged.
Verifier/extractor tests cover UTF-8 Unicode passwords, but the current UI does
not enumerate accented/emoji passwords. Legacy password byte encodings other
than UTF-8 are not supported. Long random passwords normally remain infeasible.

The native core requires current browsers with CompressionStream and
DecompressionStream supporting `deflate-raw`, plus Web Crypto and Workers.
No WASM/network fallback is configured. Browser incompatibility is an error,
never fabricated recovery.

## Format-backend architecture and validated capabilities (2026-10-14)

- `format-backend.js` handles genuine password-specific RAR4, RAR5 and
  AES-256 7Z operations via pinned 7-Zip 24.09 WASM, and encrypted PDF via
  pinned qpdf WASM. `format-worker.js` hosts each engine; ZIP retains the
  original independent and self-contained classic Worker.
- `SearchRun` still schedules deterministic, nonoverlapping dictionary and
  brute-force ranges, tracks actual checks, pauses/stops at candidate
  boundaries and independently confirms a match using a **new Worker**.
- Encrypted RAR/7Z archive headers are checked without decompressing entire
  payloads on every guess. Following a plausible match, a fresh runtime
  reads the archive, applies file/path/output checks, tests full contents,
  extracts to its isolated virtual filesystem, validates byte lengths and
  returns Blob objects. The existing ZIP writer builds ordinary unencrypted
  ZIP downloads, and individual-file downloads remain user initiated.
- PDF initial inspection reads the referenced Standard Security `/Encrypt`
  dictionary and revision. qpdf verifies the actual opening password; an
  owner-only match is rejected. Decrypted output is then rechecked by qpdf
  without a password. Independent browser tests reopen each export using
  Python pypdf; only a real password-free PDF is presented.
- CPU-only; no fake GPU or Hybrid path. Actual attempt rates depend on the
  file format, parameters, browser and workstation. **No physical RX 9060 XT
  benchmark or validation has been claimed.**
- Shared dictionary assets are not duplicated. The ZIP demo generator is
  unchanged. There is no RAR/7Z/PDF creator in the browser.

### Tested subsets and limits

- RAR4: genuine independently produced header-encrypted RAR4 test file,
  wrong/correct passwords, real extraction and original bytes.
- RAR5: independently produced header-encrypted RAR5 test file, real
  password checks and original extracted data.
- 7Z: independently created AES-256 + encrypted-header LZMA2 archive,
  wrong/correct passwords; both individual and recovered-ZIP downloads
  were reopened independently.
- PDF: independent pypdf files encrypted with RC4-40 (R2), RC4-128 (R3),
  AES-128 (R4), AES-256 (R6); wrong/correct passwords and genuine
  password-free PDF export reopened by a second PDF parser. Other revisions
  must not be advertised unless separately tested.
- All non-ZIP inputs are capped at 8 MiB; the existing output
  bounds and path/entry limits apply. For archives with encrypted headers,
  decoded sizes are inspected after a successful candidate and **before**
  full decompression. A browser WASM decoder is not a formally memory-safe
  sandbox; memory limits and compression codecs outside this tested subset
  still require additional validation. WASM Workers can be terminated.
- **Unsupported/not guaranteed:** RAR multivolume, SFX, unusual compression
  modes and split sets; PDF non-Standard handlers / XFA-dependent content,
  signatures invalidated by rewriting, some incremental-update variations,
  untested PDF R5; 7Z exotic codecs or oversized solid dictionaries.
  Arbitrarily long random passwords remain computationally infeasible.
