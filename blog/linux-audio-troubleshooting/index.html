No Sound on Linux? Troubleshoot PipeWire, WirePlumber, ALSA & Bluetooth

From wpctl connection errors to missing S/PDIF beginnings: find the right diagnostic layer, understand the evidence and make only justified changes.

    Start here: find the failing layer

    If wpctl status reports Could not connect to PipeWire, begin with the connection path. If it lists your speakers, begin with routing and mute. Reinstalling the sound server before making this distinction can turn a small routing problem into a package migration.

    Open your desktop’s application menu and launch Terminal. Run a command as the user whose sound is broken, one command at a time. Do not copy a leading $ prompt. The examples here omit it. Never add sudo to wpctl or systemctl --user: root has a different session. A command that is not installed is a missing tool, not evidence that your sound card has disappeared.

    What this guide can establish. The assistant branches on your observations. It does not inspect your computer, run commands, collect logs or certify a fix. The guide and examples were checked against upstream documentation on 27 October 2026; no physical audio-hardware reproduction is claimed.

    How Linux audio actually reaches a speaker

    A working card is only the beginning. The kernel driver exposes ALSA controls and playback/capture interfaces. An application needs a compatible interface, an available server, a selected route and a device configuration the hardware can use. A successful ALSA card listing proves registration at that layer; it does not prove the browser is sending a stream to that card.

    PipeWire runs the multimedia graph. Applications can use its native API or compatibility libraries. PulseAudio-protocol clients normally reach pipewire-pulse on a PipeWire desktop. ALSA applications can reach PipeWire through the distribution’s ALSA plugin, while a client deliberately opening hw: accesses ALSA directly and may compete for the device. JACK applications can use PipeWire’s JACK implementation when the corresponding libraries are selected; a separately running JACK server is a different arrangement.

    WirePlumber supplies policy: which devices to expose, profiles to activate, routes to restore and streams to link. It loads hardware monitors and controls graph objects. It is not a serial audio-processing stage between PipeWire and ALSA. Bluetooth takes the BlueZ/Bluetooth route instead of pretending to be a local ALSA card. See the PipeWire overview and WirePlumber components.

    TermPractical meaning
    Device / cardConfiguration object for hardware; one card can expose several endpoints.
    SinkPlayback destination: speakers, HDMI, headphones or a virtual output.
    SourceCapture origin: microphone or a sink’s monitor. A monitor is playback capture, not a microphone.
    StreamAn application’s active playback or recording connection.
    ProfileAvailable input/output combination, such as analog stereo duplex or digital output.
    Port / routePhysical or logical selection within that configuration, such as headphones versus line out.

    Read first, repair second

    Use a quiet, known local audio file for playback comparisons. Confirm that the amplifier is on, the cable is in the intended socket and physical volume is low. A muted application and a sleeping digital receiver can produce the same silence for entirely different reasons. Write down what changed just before the problem: update, docking, a headset call, resume or switching monitors.

    The following commands are observations. They do not apply a repair. Commands that open a client connection can trigger normal socket activation; “read-only” means they request no configuration change. The command reference includes permissions, expected evidence and limits. A reported state is a lead, not a verdict.

    Diagnosis · read only

    wpctl status

    Read sinks, streams and the default marker as the logged-in desktop user; no route is changed.

    Evidence and limit: A visible expected sink confirms graph exposure. A different default or application target is a routing lead; a missing sink needs device/profile investigation.

    Diagnosis · read only

    systemctl --user status pipewire.service pipewire.socket wireplumber.service pipewire-pulse.service --no-pager

    Read audio user-unit state from the affected desktop account, without sudo. Some units are optional on a given distribution.

    Evidence and limit: A failed unit needs its first error; Unit not found can mean an absent package or a distribution-specific name. Running services alone do not prove routes exist.

    Diagnosis · read only

    journalctl --user -b -u pipewire.service -u wireplumber.service -u pipewire-pulse.service --no-pager -n 200

    Read this account’s startup errors and configuration context; no service is restarted.

    Evidence and limit: A named missing module points to packaging or configuration; D-Bus/runtime failures point to session setup. Preserve the first failure before reset-failed hides its prominence.

    In the status listing, match names to the actual device and note the default marker. In the journal, read the first meaningful error at the failure time. A warning about an unused optional component is not equivalent to a failed audio graph. A nonzero exit from systemctl status is expected when a named unit is inactive or absent; read the displayed state.

    “Could not connect”: server, socket or compatibility bridge?

    The message establishes that this client did not connect to the selected PipeWire server. It does not identify why. A stopped server, wrong runtime directory, intentional remote override, missing package or different user can all lead here. WirePlumber can fail too, but a healthy PipeWire server can still accept a client while policy is missing. Keep these failures separate.

    Inspect the service and socket. On a socket-activated installation an inactive service can be normal until a client connects. An active listening socket is evidence about activation, not evidence of a working speaker route. If a unit is masked, find out who masked it and why before undoing the policy. Do not enable standalone PulseAudio and its PipeWire replacement together as an experiment.

    Diagnosis · read only

    systemctl --user status pipewire.socket pipewire.service pipewire-pulse.socket --no-pager

    Normal user; inspect loaded and activation states, without starting or enabling a unit.

    Evidence and limit: Active (listening), running, failed, masked or not-found are different states. Socket availability does not establish routing.

    Diagnosis · read only

    pactl info

    Normal user; identify the reachable PulseAudio-protocol server.

    Evidence and limit: Read Server Name and default devices. Refused can mean a stopped bridge, wrong socket or absent server; it is not proof of missing hardware.

    pactl info identifies the reachable PulseAudio-protocol server. A name containing “on PipeWire” identifies the compatibility server; a standalone PulseAudio system may have no reason to offer wpctl at all. If wpctl works but pactl cannot connect, inspect pipewire-pulse, its socket and any PULSE_SERVER override. Native and PulseAudio-protocol applications can fail differently.

    Scoped action: start one intended service. If the installed PipeWire desktop configuration expects WirePlumber, the unit is present, currently stopped and its journal shows no unresolved configuration failure, this starts that service for the current user. It does not change boot-time enablement. Existing audio policy can change when it starts.
    systemctl --user start wireplumber.service
    Return path: if it was stopped before this deliberate test, systemctl --user stop wireplumber.service returns that service to stopped state. Stop only the test service; stopping the session manager interrupts policy management. If a service fails again, retain the first error instead of repeatedly restarting it.

    For “Device or resource busy”, identify the owner rather than killing every sound process. PipeWire holding a PCM is often normal. A second direct ALSA client or another server is a more specific lead. The shared ALSA ownership case contains the read-only owner check and its precautions.

    The user session matters, especially with minimal desktops

    Run the check inside the affected local desktop login. A root terminal, su, SSH login or container is not automatically the same audio environment. On a normal systemd/PAM login, the runtime directory belongs to the user and is commonly /run/user/<UID>. PipeWire uses runtime and remote environment variables to find the socket. The user manager and D-Bus session are related infrastructure, but an unavailable user bus is not the same error as a failed audio-device probe.

    Diagnosis · read only

    id -u

    Normal user; read the effective numeric user ID.

    Evidence and limit: Compare with the affected desktop account; UID alone does not prove the correct runtime environment.

    Diagnosis · read only

    printenv XDG_RUNTIME_DIR PIPEWIRE_RUNTIME_DIR PIPEWIRE_REMOTE PULSE_SERVER

    Normal user; read socket-related environment values in this terminal.

    Evidence and limit: Optional unset variables are omitted and may make printenv exit nonzero. Compare runtime with the UID; investigate an unintended override without exporting guessed replacements.

    Do not “fix” this by inventing XDG_RUNTIME_DIR, changing ownership of another user’s runtime directory or hardcoding UID 1000. Compare a fresh terminal opened from the desktop first. If your own startup file exports a stale remote, save that exact file before removing that one override; restore it to roll back. For XMonad/dwm/startx setups, inspect the distribution’s supported login/session setup rather than copying another desktop’s environment blindly. X11 versus Wayland does not replace ALSA or PipeWire; session startup, permissions and portals can nevertheless differ. See pam_systemd.

    PipeWire runs, but nothing useful is audible

    Work from the graph toward the cable. Is the desired sink present? Is it default? Is the app playing into it? Is the sink muted? Does the selected card profile expose the required port? A monitor that was recently connected may become a playback target even when your speakers remain on the analog card.

    Diagnosis · read only

    wpctl get-volume @DEFAULT_AUDIO_SINK@

    Read the current default output’s volume and mute state without changing it.

    Evidence and limit: [MUTED] explains silence at that sink; a normal level does not rule out application mute, hardware mixer mute or an incorrect route.

    Diagnosis · read only

    pactl list cards

    Normal user; read card profiles, active profile and ports.

    Evidence and limit: Off or another output-only profile can explain a missing sink. A listed profile does not establish audible output; select only a compatible available profile.

    A default applies to streams that use policy-selected destinations; existing streams can retain an application-specific target. Use your desktop sound controls or pavucontrol to move the actual playing stream. Record the old target before testing and restore it if the comparison fails. Likewise record the old card profile and port: profile switches can remove and recreate endpoints, interrupting playback and recording.

    Scoped action: unmute the confirmed default. After confirming that the default is the intended output and its previous state was [MUTED], lower the physical volume first. This changes that sink’s mute state and can immediately produce sound.
    wpctl set-mute @DEFAULT_AUDIO_SINK@ 0
    Undo that test: wpctl set-mute @DEFAULT_AUDIO_SINK@ 1 restores mute only while the same sink is still default. If defaults changed, resolve the current sink ID again and restore the original device’s recorded state. Do not treat an arbitrary ID from a screenshot as your device.

    To choose a default from the command line, wpctl set-default ID takes a sink or source node ID from your current status, not a card ID. Write down the old default first; setting its current node ID restores the previous selection. For a physical mixer issue, use alsamixer, F6 to choose the card, F3 for playback and F4 for capture. Opening the mixer is not a reset; changing a switch is an action. Note original values and change only the relevant playback control.

    WirePlumber 0.4 and 0.5: do not mix configuration formats

    Check wireplumber --version before using a rule from a search result. WirePlumber 0.5 changed configuration to SPA-JSON and does not automatically migrate old Lua configuration. A copied full wireplumber.conf can also keep an old component layout alive after an upgrade. Upstream recommends fragments rather than maintaining a stale private copy of the vendor file.

    On 0.5, user fragments normally live in ~/.config/wireplumber/wireplumber.conf.d/, or the equivalent under a customized XDG_CONFIG_HOME. On 0.4, legacy main.lua.d/bluetooth.lua.d instructions belong to a different format. Renaming a Lua file to .conf is not migration. Follow the upstream migration guide and fragment documentation.

    When the journal names your fragment: keep a backup outside the loaded fragment directory, then rename only that implicated file to a suffix that does not end in .conf. Do not move the whole configuration tree. Restart only WirePlumber when its configuration is the failing component; warn other users of ongoing recordings first.
    systemctl --user restart wireplumber.service
    Rollback: restore the exact fragment to its original name and restart WirePlumber again. A restart interrupts policy/device management; it cannot undo changes to unrelated applications. Compare the new journal before deciding whether the fragment was the cause.

    Dummy Output and missing ALSA hardware

    “Dummy Output” tells us there is no usable playback sink in that server context. Separate four observations: no ALSA card; a card without the needed PCM; a PCM without a PipeWire node; a node hidden by profile/route choices. Bluetooth is a separate hardware-monitor path and is not expected in aplay -l.

    Diagnosis · read only

    cat /proc/asound/cards

    Read registered ALSA cards as your normal user; this does not initialize a playback stream.

    Evidence and limit: No expected card places the issue below PipeWire routing. A present card without playback PCMs still needs codec and profile checks.

    Diagnosis · read only

    aplay -l

    Normal user; enumerate hardware playback PCMs, without playing sound.

    Evidence and limit: Match card and device names. A PCM list does not prove server routing, and it excludes capture-only and Bluetooth paths.

    Diagnosis · read only

    lspci -nnk

    Normal user; read PCI identities and driver binding where exposed. Some details may be restricted.

    Evidence and limit: Kernel driver in use is binding evidence, not proof that every codec initialized. USB devices need lsusb instead.

    Diagnosis · read only

    journalctl -k -b --no-pager -n 350

    Read kernel probe messages with journal access if necessary. Compare snd_hda, SOF and USB events with the expected device.

    Evidence and limit: Missing firmware or codec probe errors justify driver-layer work. A polling fallback warning alone may be harmless if the card and playback work.

    HD-Audio controllers and codecs are different pieces; the name snd_hda_intel does not mean “Intel hardware only”. A PCI device being listed does not prove a codec initialized. For SOF-based systems, a journal that names a missing firmware/topology file is useful evidence: match the exact filename and platform to your distribution’s firmware packages. Do not guess DSP driver switches, probe_mask or model= options from another laptop.

    A kernel warning about switching to polling can be survivable; repeated probe failures and a missing card are a different situation. Compare with an already-installed previously working kernel if the loss followed an update. Keep the current and old boot options so that comparison is reversible. The kernel’s HD-Audio notes explain why hardware-specific quirks need evidence.

    Microphones: source, capture path and app permission

    Choose the physical source, not “Monitor of …”. Check a laptop privacy switch or headset mute before raising gain. Confirm the app selects that source; changing a system default does not necessarily replace a stored application selection. A moving desktop meter with no app meter suggests a different layer than a silent input everywhere.

    Diagnosis · read only

    arecord -l

    Normal user; list capture PCMs without recording or creating a file.

    Evidence and limit: A capture interface is registration evidence, not a live microphone signal; absence calls for hardware/profile investigation.

    Diagnosis · read only

    wpctl get-volume @DEFAULT_AUDIO_SOURCE@

    Normal user; read the default source volume and mute.

    Evidence and limit: [MUTED] identifies a mute at that source. The app may select another source; a normal level does not prove a signal.

    arecord -l enumerates capture hardware without recording. It does not prove the microphone receives a signal. For a deliberate recording test, use your desktop recorder with a clearly selected source, record only your own test speech, then delete the recording through your file manager when done. Review both system microphone access and the browser’s per-site permission. The ALSA recording guide documents capture switches and the limits of default-device tests.

    Why a Bluetooth headset suddenly sounds like a telephone

    Classic Bluetooth A2DP is normally the high-quality playback path. HSP/HFP provide bidirectional headset audio, with quality depending on codec and hardware support. Opening the headset microphone can therefore change playback quality. This is often a profile transition, not a broken sample rate or an underpowered CPU. A separate USB/analog microphone can let classic A2DP playback remain selected.

    Watch the profile while the call app starts and stops capture. Close the microphone stream before comparing A2DP again. Record the previous app input and headset profile; restore them to undo the test. Do not disable every codec or globally force a profile before establishing the transition. LE Audio is a separate capability question: controller, headset, BlueZ, PipeWire and distribution configuration all matter.

    For no connection at all, inspect the paired device in Bluetooth settings and verify it is not busy with another host. A BlueZ “Connected” state is not proof of a PipeWire sink. Bluetooth plugin packaging and active-session ownership are next checks. WirePlumber’s Bluetooth configuration describes seat monitoring; documented settings describe automatic profile switching. Do not disable seat monitoring merely to bypass the wrong login context.

    One app, Steam, OBS, Discord or a browser is silent

    If another app works on the same sink, keep that working baseline. Check the failing app’s mute, backend, output device and active stream. In OBS, a moving source meter does not prove that source is on the recording or streaming track you selected. In a browser, tab/site playback mute and microphone permission are separate. In Steam/Proton, establish whether the game creates a stream before changing global server settings or deleting prefixes.

    Diagnosis · read only

    pactl list sink-inputs

    Normal user; read active PulseAudio-protocol playback streams.

    Evidence and limit: Compare Sink, mute and volume for the playing app. Native PipeWire streams need wpctl/pw-cli inspection too; no stream while idle is normal.

    Diagnosis · read only

    flatpak info --show-permissions APP_ID

    Normal user; replace APP_ID with the installed application identifier. Read declared permissions.

    Evidence and limit: Inspect sockets and compare app/user overrides in your permission controls. A declared audio permission does not prove a running host bridge or a site’s microphone permission.

    For Flatpak, replace APP_ID with the installed ID. Its pulseaudio socket permission covers audio access even when the host server is PipeWire. A missing permission, an app override and a failing host compatibility server are different leads. Inspect first; use the app’s supported permission controls for a justified change and record the previous permission to restore it. Avoid blanket filesystem/device permissions. See the Flatpak permission reference.

    Crackles, buffers and XRUNs: correlate before tuning

    The graph processes audio in blocks. Quantum divided by sample rate gives the nominal block duration: 256 frames at 48 kHz is about 5.33 ms, not total microphone-to-speaker latency. Smaller blocks reduce one component of delay but leave less time to meet deadlines. Device buffers, converters, resampling, transport and the application add their own latency.

    Diagnosis · read only

    pw-top -b -n 5

    Read five graph snapshots as the desktop user while the affected audio is already playing; this does not change graph settings.

    Evidence and limit: Compare ERR changes with WAIT/BUSY relative to quantum. Historical ERR alone is weak evidence; the graph driver can count faults propagated from another node.

    In pw-top, observe QUANT/RATE, WAIT, BUSY and changes in ERR while the fault is audible. ERR includes XRUNs and other errors. A cumulative value from earlier playback does not prove the present crackle is a scheduling failure. Driver and follower nodes account for different timing; a driver can report a graph-wide miss caused elsewhere. Read the column definitions rather than treating a single large number as a diagnosis.

    Compare the same local file at idle and under the workload that triggers the symptom. Then compare another output. USB resets call for transport/power/cable investigation, not a larger graph quantum. Bluetooth packet loss and clipping can sound like buffer trouble. If a professional app offers its own buffer setting, record it, change one step and compare; restore it if ineffective. Inspect realtime scheduling support and the distribution’s limits before changing priorities. Do not run the whole server as root.

    Expert inspection: nodes, parameters and a graph snapshot

    Diagnosis · read only

    pw-cli ls Node

    Normal user; list nodes in the selected PipeWire instance.

    Evidence and limit: Read IDs, node names and media classes. Visibility is not proof of a link or successful hardware playback.

    Diagnosis · read only

    pw-dump

    Normal user; print the current graph as JSON to the terminal; no file or upload is created.

    Evidence and limit: Includes devices, nodes and other objects, potentially private names/paths. Inspect locally; a snapshot is not a latency trace or proof of a repair.

    Match names and object types before using an ID. A graph snapshot can contain application names, paths and identifying properties. Keep it local and redact before deliberately sharing. Do not publish a full dump just because a support form accepts it. The PipeWire property reference distinguishes graph timing from ALSA-specific buffers; there is no justified universal “crackling fix” here.

    My missing first two seconds: S/PDIF silence is not one problem

    My old digital S/PDIF setup regularly swallowed roughly the first two seconds after a pause, seeking in a video or a short silent interval. Short notification sounds could disappear completely. That experience led me to write spdif-fix. I no longer use S/PDIF at this PC, but the distinction it taught me still matters: steady playback latency and a lost beginning after silence are different symptoms.

    There are several possible transitions. An application can stop or disconnect its stream. Policy can suspend a node and close its ALSA device after idle. A digital receiver can lose its carrier/format synchronization or mute digital silence on its own. Keeping the server’s device open addresses one transition; it cannot promise that every external amplifier remains locked. These are hypotheses to compare, not a retrospective measurement of my receiver.

    Diagnosis · read only

    pactl list sinks short

    Normal user; compare the exact sink during playback and after idle.

    Evidence and limit: SUSPENDED is often expected. Correlation with lost beginnings is a hypothesis to test, not proof of receiver synchronization behavior.

    Compare the exact sink during playback and after the interval. If it becomes SUSPENDED, a device-specific policy test is reasonable. If it remains active yet the receiver drops its signal indicator, investigate receiver behavior and the transport too. A running stream carrying zeros can still be treated as silence. Conversely a nonzero keepalive is not guaranteed inaudible and may change mixing, power use or passthrough behavior.

    A narrowly scoped WirePlumber 0.5 example

    First check wireplumber --version. This example uses the documented 0.5 configuration format. From wpctl status, choose your digital sink’s current ID, then inspect it to obtain the exact node.name. Replace the placeholder below with that value; do not use a wildcard matching all outputs. An ID is not a permanent name.

    Diagnosis · read only

    wpctl inspect ID

    Normal user; replace ID with the current sink node ID from wpctl status.

    Evidence and limit: Copy the exact node.name for a narrowly matched rule. Numeric IDs may change after reconnects and are not permanent configuration identifiers.

    Before editing: use your actual XDG configuration location. Create the user fragment directory if it does not exist. Choose the filename 51-audio-rescue-spdif.conf only if it is unused; if it already exists, stop and back it up outside the loaded directory before editing. In a text editor, put the following content in that file. This is configuration text, not a shell command.
    monitor.alsa.rules = [
  {
    matches = [
      { node.name = "REPLACE_WITH_EXACT_DIGITAL_SINK_NODE_NAME" }
    ]
    actions = {
      update-props = {
        session.suspend-timeout-seconds = 0
      }
    }
  }
]

    Save it under ${XDG_CONFIG_HOME:-$HOME/.config}/wireplumber/wireplumber.conf.d/51-audio-rescue-spdif.conf. Restart only WirePlumber using the restart command above when no recording depends on it. Inspect its journal and the matched sink again, then repeat pause/seek tests with every other setting unchanged. Upstream documents that zero disables node suspend and leaves the ALSA device busy; it can increase power use and prevent another direct client from acquiring the device. See ALSA node rules.

    Rollback: rename only the fragment you created to 51-audio-rescue-spdif.conf.disabled, which does not end in .conf, then restart WirePlumber again. If you edited a pre-existing file, restore its separately saved original instead. Recheck idle behavior. Do not delete the whole WirePlumber state/configuration tree. The rule is not a 0.4 Lua rule and is not a fix for a whole-system resume failure.

    How my S/PDIF fix helped me at the time

    On my old S/PDIF setup, the sound card kept returning to power-saving mode even though I had already disabled it. After pausing or seeking, the beginning of the audio would regularly disappear. My S/PDIF fix helped me with exactly that problem: it played a continuous tone that I could not hear. This kept the sound card active instead of letting it return to power-saving mode. I used this workaround until I switched to an analog RCA connection.

    The keepalive playback is provided by soundfixforautostart.sh, which starts a very low-level SoX tone. For my setup at the time, this was a practical solution to a particularly annoying everyday problem. I describe how I used it in more detail in the S/PDIF article.

    Technical context for the older menu script

    Continuous playback and the additional repair menu are different approaches. The menu unloads PulseAudio’s idle module and edits a system PulseAudio file; its PipeWire branch comments matching text in a copied pipewire.conf. It does not create a current WirePlumber rule. The named ALSA PCM definition alone does not start playback either.

    When adapting this to another system, the distinctions between node suspend, the ALSA device and the digital receiver explained above still matter. Back up existing configuration separately before using the menu: its reset does not establish whether the tool created an existing ~/.asoundrc, and fixed .bak names can replace earlier backups. Do not mix a PCM keepalive with encoded passthrough. To end a keepalive test, stop the playback process you started.

    HDMI and DisplayPort: a PCM is not a connected receiver

    GPU audio can be registered even when the monitor, adapter or receiver exposes no usable audio capability. Check the actual display input, cable, receiver power and whether the screen has audio at all. Some adapters do not carry the desired format. ELD describes the connected receiver’s advertised audio capabilities; choose the file for the actual card and connector instead of assuming the first one.

    Diagnosis · read only

    cat /proc/asound/card0/eld#0.0

    Replace card0 and eld#0.0 with the ELD file for the relevant GPU connector shown under /proc/asound; ordinary read access is usually sufficient.

    Evidence and limit: monitor_present, eld_valid, monitor_name and SAD entries describe receiver detection and audio formats. Zero validity or no SAD needs a cable/receiver check before profile forcing.

    Read monitor_present, eld_valid, the monitor name and supported audio descriptors together. A valid record does not prove the correct profile or app route. If detection fails only after docking or sleep, compare ELD and the graph before and after reconnecting during a safe test; reconnecting interrupts display/audio. Restore the original connection and profile afterward. Avoid forcing a permanent profile to cover an unstable physical link.

    USB DACs: transport, formats and clocks

    Diagnosis · read only

    lsusb

    Normal user; enumerate USB identities without changing the audio configuration.

    Evidence and limit: Presence identifies bus enumeration, not an ALSA driver or working audio interface. Absence points to connection/transport first.

    First ask whether USB enumerates the device, then whether ALSA registers its audio interfaces, then whether PipeWire exposes the expected nodes. Test a direct port and a known good cable before blaming the sound server. Keep the original connection documented so you can restore it; changing ports can change device identity or stored routes.

    For an interface with rate/clock errors, the matching /proc/asound/cardN/streamM file lists supported formats. Replace both indices with your device’s values. Advertised rates do not establish external clock lock. Compare the application’s requested rate and channels with the correct playback/capture interface. A disconnect/reset in the kernel journal points to a different layer than growing graph deadline errors.

    5.1 / 7.1, channel maps and encoded passthrough

    Channel count, channel order and encoding are separate questions. Analog surround needs the right profile, jacks and cabling. HDMI multichannel PCM depends on receiver capability. Conventional S/PDIF generally carries stereo PCM or compatible compressed surround; selecting “7.1” cannot create the bandwidth for arbitrary multichannel PCM. A player’s passthrough setting also needs a codec the receiver can decode.

    Compare stereo PCM first without a keepalive, then a known channel-identification sample at low volume on the intended profile. Record the original profile, player passthrough setting and any channel map before a targeted test; restore them afterward if it fails. Do not apply one forced audio.position map to every card. See the shared digital-profile case for IEC958 controls and its precautions.

    After system suspend: compare before and after

    A system sleep cycle is more than an idle playback node. USB can reconnect, GPU receiver information can change and a controller/firmware resume can fail. Capture a pre-sleep graph and compare device names, profiles and routes after resume. IDs may be reassigned. Read the kernel journal and the affected user journal around that event before restarting the service and erasing the most useful state.

    If hardware disappears from ALSA, a routing tweak cannot restore its registration. If hardware remains but the app points at a retired endpoint, fix that route. If both remain, retain timestamps and the first error for a focused driver/server report. Compare a previously working installed kernel only when the evidence suggests a regression; keep a working boot option available.

    Debian, Ubuntu, Fedora and Arch: package names are not interchangeable

    Debian 13’s pipewire-audio metapackage includes the recommended desktop set, including WirePlumber, the PulseAudio bridge, ALSA integration and Bluetooth plugin. The installed package pipewire alone does not establish all those interfaces. Ubuntu releases can ship different WirePlumber branches: 24.04’s package family uses 0.4 libraries, while 26.10’s manifest lists a 0.5 daemon. Check the installed version, not the article date.

    Fedora calls the PulseAudio replacement package pipewire-pulseaudio; do not assume Debian’s package name. Arch’s PipeWire reference describes separate compatibility packages and recommends a coherent system upgrade. Preview package transactions and removals before proceeding. This guide deliberately does not present one reinstall command as a universal repair. On a non-systemd installation, use its supported service manager; the graph and hardware distinctions still apply.

    Questions that come up during diagnosis

    Should I run wpctl with sudo?

    No. Use the affected desktop account. A root process can have the wrong runtime and session, hiding the actual issue.

    Does SUSPENDED mean my sound is broken?

    No. It is often normal idle power management. Correlate the transition with your symptom and compare the exact device before testing a targeted rule.

    Can I delete all audio configuration to start over?

    Do not make that the first step. Read the journal, preserve the configuration and isolate one implicated fragment. A full reset destroys evidence and unrelated preferences.

    Will changing the default fix every application?

    Not necessarily. An existing stream or saved app setting can retain another target. Inspect the active stream too.

    Does a higher buffer fix every crackle?

    No. Deadline misses, clipping, transport loss and clock errors require different evidence. Compare counter changes during the audible fault.

    What to keep when the result is still uncertain

    Keep your distribution and installed PipeWire/WirePlumber versions, exact device model/USB or PCI identity, symptom trigger, first relevant error and one controlled before/after comparison. Keep raw logs local and redact usernames, paths, hostnames and device addresses before deliberately sharing selected lines. The assistant has no log-upload field and makes no repair decision for you.
