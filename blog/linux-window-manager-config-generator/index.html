From installation media to first login

  1. Back up your files and get official installation media. Verify its signature or checksum as documented. Try a live system or virtual machine first.
  2. Check the destination disk and partition plan. Choose a full desktop if you want a file manager, network controls and settings on day one.
  3. Update the installed system through your distribution’s normal route. Install the applications and session you want before leaving your current session.
  4. Open the terminal and browser from your current session. Back up existing configs and validate new ones. Then select the new session at login.

APT and DNF install from configured repositories and resolve dependencies. On Pacman, install against a fully updated system. Portage applies profiles and USE flags. NixOS builds the system from its declaration. Flatpak applications use their own runtimes and sources. Update instructions for all eleven distributions

Recover from an empty first desktop

  1. Try the terminal shortcut from your generated list. The default is Super+Enter.
  2. Switch to a free text console, often Ctrl+Alt+F3. Some devices also need Fn. Sign in as your usual user.
  3. Check that your browser, terminal and launcher are installed. For example, command -v kitty should give a path if you chose Kitty. Use the builder’s validation command to check config syntax.
  4. Rename the new configuration file to an unused name and restore your separate backup. If you changed the NixOS setup, you can select the previous generation from the boot menu when available.
  5. On a systemd system, systemctl status display-manager shows the login manager status. journalctl --user -b may show clues about the session. Return to the login screen and choose your existing graphical session. The function key for returning varies by distribution.

You can add a bar, wallpaper and notifications later. For a fresh WM, get the terminal, launcher and recovery path working first.

X11 or Wayland?

Under X11, an X server manages display and input, and a separate window manager arranges windows. Wayland is a protocol in which the compositor handles display, input and window management together. XWayland runs an X server within a Wayland session and supports many older X11 applications. Check the login menu for the sessions actually installed. Wayland documentation

TaskWhat to check
AMD and NVIDIAAMD’s open graphics stack combines kernel, firmware and Mesa. On NVIDIA, options depend on GPU model, driver version and compositor. NVIDIA’s open kernel modules still use NVIDIA userspace components. Check support for the whole session. NVIDIA on ArchWiki · AMDGPU on ArchWiki
Steam, Proton and WineOlder games and clients may run through XWayland. Native Wayland support depends on the program and Wine version. Check Vulkan, any needed 32-bit drivers, controllers and the exact game. Valve Proton
Capture and sharingOn Wayland, the ScreenCast portal and PipeWire often supply a selectable stream. Desktop, portal backend and app must work together. X11 applications often access screen data through X11. Try sharing a single window with your app. ScreenCast portal
Monitors and older appsCheck mixed refresh rates, scaling and fullscreen on both monitors. On Wayland these depend on the compositor. XWayland can have scaling and input limits for older apps. Test global shortcuts and capture separately.
Remote accessForwarding an X11 application over SSH, sharing a running session and connecting before login are separate tasks. Wayland sharing, consent prompts and unattended access depend on the desktop and tools. Test the exact workflow.
