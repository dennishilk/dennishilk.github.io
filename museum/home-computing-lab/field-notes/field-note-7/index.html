FIELD NOTE #007 · STARTED 12 SEP 2026 · FINALIZED 15 SEP 2026

I BOUGHT A €35 CISCO PHONE.
NATURALLY, I PUT DOOM ON IT.

It started as a SIP/H.264 thin client. It ended with the Cisco itself running DOOM natively, with its own ARM CPU, framebuffer, physical keypad, local sound and an offline cold boot.

Short version

Can a Cisco CP-9951 run DOOM?

Yes. Natively, locally, persistently and offline.

The final v.666 build executes on the phone's ARMv6 CPU, renders directly to /dev/fb1, reads the real Cisco keypad from /dev/input/keypad0, produces audible sound through the phone's local media path, survives reboot and launches from Applications → Doom.

Morning: a €35 office phone arrived

The experiment started with a used Cisco Unified IP Phone CP-9951. The original plan was simple reconnaissance: understand provisioning, SIP, video, the local hardware and whatever useful interfaces Cisco had left exposed.

The phone stayed on its normal Cisco firmware, sip9951.9-2-1. Cthulhu already provided DHCP/TFTP provisioning and Asterisk handled SIP. One engineering requirement was established immediately and never revisited: the cat background stays.

Stage 1 — Werner on 111

The first deliberately unnecessary application was Werner. Provisioning enabled the CP-9951's H.264 receive capability, Asterisk routed extension 111, and a dedicated Baresip endpoint delivered 640×480 H.264 video plus PCMU audio.

Stage 2 — live DOOM on 666

The next target was extension 666. DOOM still ran on Cthulhu under Wayland/Sway:

Moving from a buffered media-file path to v4l2loopback removed the multi-second delay and made the display near realtime.

Recording 03 — the Cisco really controls DOOM

The last missing part of the streamed setup was input. Before we understood the phone's local Linux input stack, the CP-9951's number keys sent DTMF over RFC4733 during the call. A locally bound Asterisk AMI connection fed those events to a small Python bridge, which generated real keyboard events through Linux /dev/uinput.

Important chronology:

At this point DOOM still ran on Cthulhu. The Cisco was the display and the controller. Native execution came later.

The turning point — getting into the shell

Cisco provided an official SSH diagnostic-access path for this 89xx/99xx generation. This was not a bootloader exploit, firmware replacement or custom image.

The phone's SSH implementation is old enough that a period-compatible client was useful. Once the two-stage diagnostic login completed, the phone presented a real Linux shell.

The moment:

The actual experience was basically one obvious vendor-name guess — followed immediately by: “Moin. Welcome to MontaVista Linux Professional Edition Blackfoot.”

The numeric keypad, navigation cluster, softkeys, line keys, volume keys and feature buttons were measured directly. Native play needs no DTMF, SIP key forwarding or desktop-side controller bridge.

Native DOOM

DOOM engine
 → executes on Cisco ARM CPU
 → renders directly to /dev/fb1
 → reads /dev/input/keypad0
 → uses the physical Cisco controls
 → returns to the Cisco UI on exit

The navigation cluster handles movement and menus, OK confirms, * fires, # uses/opens, and the red handset button exits cleanly. No Cthulhu rendering, H.264 game stream or DTMF bridge remains in the final runtime path.

Sound: the last big runtime problem

The final build emits compact sound events to a phone-local relay/service that produces 8 kHz G.711 μ-law RTP for the Cisco media subsystem.

The physical fix was binding the RTP source to 127.0.0.1. With Ethernet present, the configured phone address can be the destination; after a cable-free cold boot the service falls back to loopback instead of failing on a missing route. Both paths were physically verified with audible DOOM sound.

Persistence: Applications → Doom

The final installation lives under:

/mnt/flash2/doom-v666

The normal Cisco Applications menu launches the local endpoint:

http://127.0.0.1:8095/launch

An isolated persistent xinetd service uses Cisco's existing boot path. The game, Freedoom IWAD and helpers survive reboot. No manual shell command is needed for normal use.

The most important design requirement

The cat background was the first important engineering decision. It remains.

Final physical proof — 15 September 2026, cable out

The final acceptance run removed the last ambiguity. Ethernet was physically disconnected before the cold boot. The phone came up from power only, Applications → Doom launched the persistent local install, the game ran on the Cisco's ARM CPU, the real keypad controlled it, sound was audible, and the red handset button returned cleanly to the Cisco UI.
